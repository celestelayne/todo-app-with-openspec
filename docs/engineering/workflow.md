# Change Workflow

**Status:** Draft v0.1  
**Last updated:** 2026-11-02

## Purpose

Define how a change moves from a branch to `main`: branching, commits, pull requests, CI, review, and merge.

`verification.md` defines which checks must pass. This document defines where and when they run. For security-sensitive and destructive operations, see `security.md`.

## Overview

```text
branch -> OpenSpec change -> implement -> commit -> local gate -> push -> PR -> CI -> review -> merge
```

## 1. Branch

Create the branch before starting the change, and before running `/opsx:propose` for OpenSpec work. Nothing is written on `main`.

- Branch from an up-to-date `main`.
- Name the branch after the OpenSpec change (for example `add-create-todo`). For maintenance work without an OpenSpec change, use a short descriptive kebab-case name.
- Use one branch per OpenSpec change.

The branch is created manually. The `/opsx:*` commands are generated by OpenSpec and do not create branches.

## 2. Commit

- Commit related changes together, in units a reviewer can follow.
- For an OpenSpec change, keep the implementation separate from the spec bookkeeping: the implementation commit comes first, then a commit that syncs specs to `openspec/specs/` and archives the change.
- Do not rewrite history, force-push, or delete branches without approval (see `security.md`).
- Never commit secrets. Commit the lockfile with any dependency change.

No commit-message convention is enforced yet.

## 3. Local Gate

Run the same checks CI runs before pushing:

```bash
pnpm check
pnpm architecture:check
pnpm test:e2e
```

For user-facing changes, also complete the browser and accessibility review described in `verification.md`. Report any check that was not run.

## 4. Pull Request

Open a pull request into `main`. The description includes:

- What changed and why.
- The OpenSpec change or issue it implements, and which requirements it satisfies.
- Tests added or updated.
- Verification commands run and their results.
- Checks not run, known limitations, and remaining work.
- Screenshots for relevant UI changes.

This is the completion report required by `AGENTS.md`, section 4.

## 5. Continuous Integration

The `Verify` job in `.github/workflows/ci.yml` runs on every pull request and on every push to `main`. It installs with a frozen lockfile and runs:

1. `pnpm check` (typecheck, lint, format check, unit and component tests, build)
2. `pnpm architecture:check`
3. `pnpm test:e2e` (Playwright, Chromium, mock API mode)

On failure, Playwright's report is uploaded as a build artifact.

When CI fails:

- Find the cause and fix it in a new commit. Do not weaken tests, disable checks, or bypass controls to get a green run.
- Do not force-push to the branch without approval.
- Changes to CI permissions or workflow configuration need approval and are made in their own change.

## 6. Review and Merge

- Human review is required for the areas listed in `verification.md` under "Human Review".
- Dependency update pull requests receive the same review as any other change and are never merged automatically (see `security.md`).
- Merge by squash so each change is one commit on `main`, then delete the merged branch.

The `Verify` check only blocks merging when it is configured as a required status check in the repository's branch-protection settings. That is a repository setting for a maintainer, not something in the workflow file. Until it is set, treat a passing `Verify` as required by convention.
